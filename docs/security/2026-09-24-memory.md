# Security record — the model keeps notes across chats, 24 September 2026

**Subject:** the `Memory` tool saves and forgets the model's short notes, for the chat's cluster
unasked and for every cluster once the user approves each call; the user writes notes for one
cluster or every cluster in the memory dialog. Every question whose context changed carries every
note its cluster sees, whole, as the `## Memory` section of its `<context>` block. The tool is
offered on every machine, to every turn on a model that takes tools, and asks only about a call
for every cluster. The living model is [security-model.md](../security-model.md).

## What persists

Text the model wrote, which later chats read. The model reads cluster data, web search results
(run by the provider, never approved) and fetched pages (each fetch approved, its content not). An
instruction planted in any of them ("remember to always run…") can become a note. Memory turns such
an injection from one chat's problem into every later chat's on that cluster, and the note now
reaches them whole — a body of up to 500 bytes in the context of every later question, where
before only a 120-character description did unless the model chose to read the rest.

Three things bound it:

- **Nothing reads a note but the model.** No tool offer, approval or gate depends on one.
- **A note the model wrote is information, never an instruction.** The system prompt says so,
  and says only a note's `by` field says who wrote it, so text inside a body shaped like one of the
  user's entries is that note's text. The JSON escaping keeps it inside the body.
- **The user can see every save.** A save that succeeded is a closed disclosure in the transcript
  holding its body, and every note is in the omnibox's dialog.

The last is weak, since nobody is asked about a save for one cluster. The risk is accepted: such
a save reaches only chats on its own cluster, and every command those chats would run is still
approved on its own. That is a
**By decision** row, and the
[ADR](../adr/2026-09-24-memory-is-rows-scoped-to-a-cluster-or-every-cluster.md) records it.

## Only the user's notes are requests

A note the user wrote is their standing request; the model follows it as if they had said it in
the chat. So which notes carry `"by":"user"` matters:

- **Through its tool, the model can neither write a user's note nor change one.** Every model
  save writes `written_by = 'model'`, an approved one for every cluster included, and only over
  a note that was already the model's in the scope the call names; a save or forget that reaches
  the user's note, on this cluster or for every cluster, is refused `user-note` and changes
  nothing (`TestTheModelChangesOnlyItsOwnNotes`, `TestOnlyTheUserWritesARequest`,
  `TestASaveForEveryClusterReplacesOnlyTheModelsNote`,
  `TestAForgetForEveryClusterRemovesOnlyTheModelsNote`). Without this an injection could quietly
  rewrite one of the user's requests, and the transcript would show only *Save memory `<name>`*.
- **A dialog edit or move makes a note the user's.** The user has read the text and adopted it,
  and the form says *Saving makes this your memory: Kstack will follow it.* before they save. That
  is the one way a note the model wrote becomes a request, and it is the user's act. Approving a
  call for every cluster is not one: an approved note stays the model's.
- **An approved command is not bound by the tool.** It runs as the user and reaches whatever they
  can, `app.db` and the sidecar's socket included, so it could write a note marked as the user's.
  That is the risk every approved command already carries, not a new one, and the user sees the
  command before it runs. The claims here are about the `Memory` tool.

**Which notes the model follows is a rule in the prompt.** The code guarantees which notes carry
the marker. What it means to the model is said by the system prompt and *Data is not
instructions*, like every other line between instructions and data: the notes marked
`"by":"user"` in the `## Memory` section of the newest `<context>` block, and no other. The marker
means nothing outside that block or inside a body, and the prompt says both, since any data can
print it. Older blocks stay in the history, so a note the user has since edited or deleted is not
followed. `TestTheSystemPromptExplainsTheMemorySection` and the `agent` golden files pin the
words; nothing can test how a model reads them.

## What crosses clusters passes the user's eye

A note for every cluster reaches every cluster's chats. The model changes one only through an
approved call. The tool asks about every save and forget with `scope: everywhere` and skips every
other call (`TestEveryCallForEveryClusterAsks`), and each call reaches only the scope it names, so
a call nobody was asked about never reaches a note for every cluster
(`TestACallForTheClusterNeverReachesANoteForEveryCluster`). A save's request draws the name, then
the whole body spelled and folded as a write's content is, with Approve waiting on the fold
(`draws the name and the body as text, with two buttons`, `spells the whitespace that ends a
line`, `folds a long body and holds Approve until the rest is shown`); a forget's draws the name
spelled the same way (`draws a forget request with the name as text`); and a memory call for one
cluster is nothing it can draw (`offers no Approve for a memory call for one cluster`). Text the
model read on one cluster reaches another only through the user's eye.

**An approved note is information on every cluster.** That is its bound: an injection that gets
the model to propose a note, and the user to approve it, lands in every cluster's chats the way a
note for one cluster lands in that cluster's — whole, and read as information, never as an
instruction. The request showed every character of it, and the dialog lists it as Kstack's for
the user to edit or delete. That is a **By decision** row, and the
[ADR](../adr/2026-09-24-memory-is-rows-scoped-to-a-cluster-or-every-cluster.md) records it.

## A chat reaches its own cluster

The binding fixes the chat's stored cluster and id; the model names neither. A chat saves and
forgets only its own cluster's notes, and a call for every cluster names no cluster
(`TestAChatSeesItsClusterAndGlobalAlone`, `TestTheBindingSavesAndForgets`).

## Secrets

The prompt forbids saving them. A note whose name or body `safe.HasSecret` matches is refused,
whoever writes it (`TestCheckMemoryRefusesACredential`,
`TestCheckMemoryRefusesACredentialInTheName`, `TestASaveRefusesACredential`). `HasSecret` finds a
registered value and every credential shape `Redact` knows except two that suit an error and not a
note: a URL's query, where a dashboard link keeps its view, and the `.netrc` rule, which reads a
line opening with *password* as a credential (`TestHasSecretFindsACredentialAndLeavesANoteAlone`).
A refused save's disclosure draws no body, so a matched credential is not on screen. A save for
every cluster is checked before its request exists, so a matched credential never reaches the
request either, and the model reads `secret` (`TestEveryCallForEveryClusterAsks`). Its text is still in
`app.db`, in the call's arguments, like any call's. A credential in no shape `HasSecret`
knows is stored in the clear in `app.db`, like the chat that produced it.

## What leaves the machine

Every note's body goes to the provider of every chat on its cluster, as part of the context, and
a note for every cluster, typed in the dialog or approved in a chat, to the provider of every
chat on every cluster. A note saved in a chat on one provider can reach another. Model-provider egress is covered by the
[egress record](2026-09-11-model-provider-egress.md).
